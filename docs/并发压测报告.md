# 拍卖出价并发压测报告

> 目的：把「条件 UPDATE 能保证不超卖」从**推理**变成**可复现的数字**。
> 脚本：`tests/stress-auction.mjs`，命令 `npm run test:stress`（需后端在 3001）。

## 为什么这么测

拍卖的价格校验不是「先查当前价 → 在 JS 里判断门槛 → 再写回去」——那样两个人同时出价会双写成功。
真正的门槛判断被塞进了 `UPDATE ... WHERE`：

```sql
UPDATE auctions SET current_price = ?, current_bidder = ?, bid_count = bid_count + 1, ...
WHERE id = ? AND status = 'live' AND end_at > ?
  AND ? >= (CASE WHEN current_price > 0 THEN current_price + step ELSE start_price END)
  AND (current_bidder = '' OR current_bidder <> ?)
```

`changes === 1` 才算赢，否则一律「手慢了」。数据库的行锁 + 这条 WHERE 是唯一裁判；
Redis 锁只是让同一个场次的并发请求排队几毫秒，减少无谓失败，**不是正确性来源**。

## 四轮实验设计

| 轮次 | 场景 | 想验证什么 |
| --- | --- | --- |
| 1 | 50 并发、同一价格、**绕过 Redis 锁** | 只靠数据库，是不是也能只有一个赢 |
| 2 | 同样 50 并发，**打开 Redis 锁** | 锁打开后结果不变（锁只削峰） |
| 3 | 50 个买家报**不同价格**，不开锁 | 多笔合法出价是否会丢写 / 幽灵计数 |
| 4 | 走**真实 HTTP** 50 并发同价 | 限流 → 锁 → 条件 UPDATE 三层叠起来的效果 |

脚本自己造一场测试拍卖（起拍 ¥100,000、步长 ¥1,000），跑完删掉，不碰演示数据。

## 几个值得记下的观察

1. **第 1 轮失败原因有两种**：少数请求在前置校验阶段读到的是「已经被改过的价」，于是被应用层门槛挡下（400）；其余走到数据库，被条件 UPDATE 挡下（409）。两条路径都是「没抢到」，说明校验做在了两层，但**最终裁判只有数据库**。
2. **第 3 轮 50 个请求成功了 38 个**，这是正确行为：每个成功价都必须 ≥ 上一价 + 步长，所以越往后叫价越难抢；最终价等于成功价的最大值，`出价次数 == bids 行数`，没有出现「价格变了但没记录」或「记录多了但价格没动」。
3. **第 4 轮 50 个请求里 30 个直接 429**：限流键是 `rate:auction-bid:<uid>`，20 次/分钟，所以真正进入业务逻辑的只有 20 个，其中 19 个抢输、1 个成功。这也是为什么 Demo 里连续快速点「确认出价」会提示「出价太频繁了」。
4. **MySQL 连接池上限是 10**，所以真正同时打到数据库的是 10 条，其余在池里排队。这不影响结论（排队本身也是串行的），但解释数字时要诚实：并发请求 50，DB 层并发度受池大小限制。

## 复跑

```bash
npm run server        # 后端 3001
npm run test:stress   # 每轮都会打印 PASS/FAIL，失败时退出码为 1
```

脚本可反复执行：固定的测试场次 id、跑前清理残留、跑后删除场次与临时会话，并在第 4 轮前清空该账号的限流桶，所以连着跑不会互相干扰。
