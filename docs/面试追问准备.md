## 一、并发与一致性（核心，必问）

### Q1. 你的法拍房怎么防止超卖 / 两个人同时出价怎么办？

**他为什么问**：这是区分「跟着教程写过 CRUD」和「真想过并发」的分水岭。答不出来，前面所有亮点都会被折算掉。

**30 秒答**

> 我没有用「查当前价 → 判断门槛 → 再写回」，那个在并发下一定双写。我把所有校验条件直接编进一条条件 `UPDATE` 的 `WHERE` 里，一次执行同时完成「判断 + 写入」，然后用 `affectedRows` 是否等于 1 来判断这一次出价是不是赢了。数据库的行锁保证这一条语句是串行的，所以同一时刻只有一个请求能把它改成功。

**再追一层**（他一定会让你写 SQL）

```sql
UPDATE auctions SET
  current_price = ?, current_bidder = ?, bid_count = bid_count + 1,
  extend_count = extend_count + CASE WHEN ? = 1 THEN 1 ELSE 0 END,
  end_at       = CASE WHEN ? = 1 THEN ? ELSE end_at END
WHERE id = ?
  AND status = 'live'                       -- 没结束
  AND end_at > ?                            -- 真的没到点（用服务端时间）
  AND ? >= (CASE WHEN current_price > 0
                 THEN current_price + step  -- 至少加一档
                 ELSE start_price END)      -- 首出价不能低于起拍价
  AND (current_bidder = '' OR current_bidder <> ?)  -- 不能自己跟自己抬价
```

`changes === 1` 才算赢，然后同一个事务里插一条 `bids` 记录；`changes === 0` 说明在我算完到写下去之间被别人抢了，回查一次当前状态，给用户具体原因（「已结束」/「你已经最高了」/「手慢了，当前价已到 ¥xxx」）。

**再再追一层**（区分度最高的一句）

> 加价门槛不是写死的常量，而是用 `CASE WHEN current_price > 0` 在 SQL 里读当前价再判断——**门槛的计算和校验发生在同一条语句里，中间没有窗口**。

**别踩**

- ❌ 别说是「事务 + 行锁解决的」。事务里如果先 `SELECT` 再 `UPDATE`，默认隔离级别下仍然是读改写，他追问一句就穿。
- ❌ 别说「加了乐观锁 version 字段」。你确实没加。
- 出处：`server/db/auction.js:332`（`placeBid`）

### Q2. 那你前面不是也查了一次拍卖吗？这不就是读改写？

**他为什么问**：这是 Q1 最自然的反击。他在测你是否真的想清楚了，还是在背结论。

**30 秒答**

> 那次查只为了**提前给出友好提示**，比如「这场结束了」「你是卖家不能出价」「出价低于 ¥103,000」，避免用户提交后拿到一个冷冰冰的失败。但它**不是裁决**——两个请求可以都通过前置校验，然后同时去打那条 UPDATE，最终只有一个能让 `changes` 变成 1。裁决永远只在数据库那一条语句上。

**再追一层**

> 换句话说：前置校验是可选的（删掉功能仍然正确，只是错误提示变难懂），条件 UPDATE 是不可选的。我把「体验」和「正确性」拆开了。

**别踩**：别嘴硬说「没有查」。有就是有，讲清它不承担正确性反而加分。

### Q3. 那你用 Redis 锁干嘛？为什么不用锁解决超卖？

**他为什么问**：大多数人会说「用分布式锁解决超卖」，他想看你是不是无脑套方案。

**30 秒答**

> 锁我用了，但它只做**削峰**，不做正确性。50 个请求同时打一条 UPDATE，会有 49 个失败回滚，白白消耗连接；加个锁让它们排队几毫秒，大部分请求在锁这层就被告知「手慢了」，数据库压力小很多。
>
> 关键设计是**三态**：拿到锁返回对象；锁被别人持有返回 `false`（直接告诉用户重试）；**Redis 本身不可用时返回 `undefined`，代码直接放行**。所以 Redis 挂了最多是变慢，不会变成「出不了价」。

**再追一层**

```js
// server/lib/redis.js:189
async lock(name, ttlMs = 3000) {
  if (!enabled || !client || !connected) return undefined   // 三态之三：不可用 → 放行
  const r = await safe(async (c) => {
    const ok = await c.set(k, token, 'PX', ttlMs, 'NX')
    if (ok !== 'OK') return false                            // 三态之二：被占用
    return { key: k, token, release }                        // 三态之一：拿到
  })
  return r === null ? undefined : r   // safe() 内部命令异常返回 null，同样降级放行
}
```

释放用 Lua 比对 token，避免「锁过期后被别人拿到，我再去 del 把别人的锁删了」。

**再追一层（验证方式）**

> 我把 Redis 停掉跑过完整流程：出价、成交、结算、通知全都正常，只是没了排行榜加速和限流。压测里第 1 轮也是**故意绕过锁**直接打数据库的，结果和开锁时一样——1 个成功。

**别踩**

- ❌ 「我用分布式锁解决了超卖」——方向反了，这是这份准备里最严重的一句错话。
- 出处：`server/lib/redis.js:185`

### Q4. 50 并发只成功 1 个，会不会是锁把请求挡住了？怎么证明是数据库在裁决？

**他为什么问**：他在验证你的实验设计能力——会不会是「结果对了但原因猜错了」。

**30 秒答**

> 我做了四轮对照，其中第 1 轮就是**完全不开锁**，让 50 个请求直接打数据库，结果还是 1 个成功、价格只被写了一次、`bids` 只多 1 条。开锁那轮（第 2 轮）结果完全一样。两轮唯一差别是失败原因不同：没锁时是「被条件 UPDATE 挡掉」，有锁时是「在锁这层就被告知手慢了」。这就排除了锁是原因。

**四轮分别在验什么**（背下来）

| 轮次 | 场景 | 结果 | 证明了什么 |
|---|---|---|---|
| 1 | 同价格 50 并发，**绕过锁** | 1/50 成功，价格只写一次 | 无敌意的对照组：数据库单独就能裁决 |
| 2 | 同价格 50 并发，**开锁** | 仍 1/50 | 锁不改变结果，只改变失败方式 |
| 3 | 50 个**不同价位**混战，不开锁 | 37~38/50 成功，最终价 = 成功出价的最大值，`bid_count == bids 行数` | 合法出价不会被误杀，也没有幽灵计数 |
| 4 | 走**真实 HTTP** 50 并发 | `{"201":1,"409":49}`（Redis 在线时还会有 429） | 限流 / 锁 / 条件更新三层叠加仍只有 1 个成交 |

**再追一层**

> 第 3 轮是最容易被忽略的：如果只测「同价位」，一个把所有请求都拒绝掉的坏实现也能「通过」。加上不同价位后，成功数必须等于「真正满足递增关系的那批人」的数量，而且 `bid_count`、`bids` 行数、成功次数三者必须严格相等——这才排除了「计数飘了但价格对」的情况。

**别踩**：别说「因为我加了锁所以只有 1 个成功」。实验结论说反了。

### Q5. 拍卖快结束时大家都挤在最后几秒出价，你怎么处理？

**他为什么问**：这是拍卖业务的经典问题（sniping），答得上来说明你懂业务，不只是懂代码。

**30 秒答**

> 做了**延时拍**：出价时如果距离结束不足 5 分钟，结束时间自动顺延 5 分钟，最多顺延 3 次。这样最后几秒的狙击一定会给别人留出反应时间，也避免了「谁的网快谁赢」。
>
> 实现上它不额外查一次——顺延判断在内存里算好，然后作为 `CASE WHEN` 的一部分写进那条 UPDATE，所以顺延和成交判定在同一次写入里完成，不会出现「价格改了但时间没顺延」。

**再追一层**：规则常量集中在 `RULES`（`extendWindowMs: 5min / extendMs: 5min / maxExtend: 3`），前端从接口拿 `rules` 渲染规则文案，改一处前后端一致。

**别踩**：别说「用定时任务扫最后 5 分钟」——那样会有扫描间隔误差，而且多实例会重复顺延。

### Q6. 拍卖到点怎么结算？为什么不用定时任务？

**他为什么问**：定时任务是很多人的默认答案，他想知道你是否有别的思路。

**30 秒答**

> 用**读路径懒结算**：不挂 cron，而是在读拍卖列表 / 详情 / 出价前调一次 `settleDue()`，它会捞出「状态还是 live 但已经过了结束时间」的场次结算掉。因为每次读都会触发，用户永远看不到「早就该结束却还在进行中」的拍卖。

**再追一层（幂等）**

```sql
UPDATE auctions SET status = 'ended', result_price = ?, winner_id = ?
WHERE id = ? AND status = 'live'
```

`changes` 为 0 直接返回——即使两个实例同时结算同一场，也只有一个能改成功，通知只发一次。结算成功后还要把房源置为 `sold` / `rented`，避免这套房在别处还能被租。

**为什么不用定时任务**

> 三个原因：一是多实例下要额外做分布式调度，否则重复结算；二是定时器有间隔，结算时间不精确；三是单机 demo 挂了 cron 就没人结算。懒结算把「什么时候结算」变成一个幂等读操作，正好绕开这三个问题。代价是「没人访问就一直不结算」——对这个业务可以接受，拍卖详情页的读取本来就必然发生。

**别踩**：别说「用 Redis 过期事件 / 消息队列延迟消息」，你没做，而且 Redis 过期回调不可靠（键可能永不被访问）。

## 二、数据与权限

### Q7. 多用户的数据怎么隔离？别人拿到我的账单 id 能付款吗？

**30 秒答**

> 账单、预约、消息三张表都加了 `user_id`，所有查询强制带 `WHERE user_id = 当前登录用户`。写接口额外做归属校验：付款前比对账单的 `user_id`，不是本人返回 **403**；删别人的消息返回 **404**（不告诉他「这条存在但不是你的」，避免探测）。
>
> 租约特殊一点：一张租约同时属于租客和房东，所以按 `tenant_id = 我 OR owner_id = 我` 过滤，两边都能看到，但只有租客能续约和退租。

**再追一层（怎么验证的）**

> 端到端测试里专门有一条线：注册第二个账号，断言它的消息 / 账单 / 预约都是 0 条；再用它去付第一账号的账单（403）、删第一账号的消息（404）；最后把第一账号的 3 条未读全部标已读，确认第二个账号的未读没被动过（还是 3 条）。

**别踩**

- ❌ 「多租户 SaaS」——这是单实例按账号隔离，说「多用户数据隔离」准确。
- 出处：`server/routes/rental.js`、`server/routes/social.js`

### Q8. 你把角色 id 当用户标识？两个账号选同一个角色会怎样？

**他为什么问**：这是设计上的一个真实缺陷，他在看你会不会发现自己的坑。

**30 秒答**

> 这套 demo 里房源 `owner_id`、拍卖 `seller_id`、租约 `tenant_id` 存的都是角色 id（比如 `gary`），这样一个角色就代表一个账号，演示时不用维护映射表。但这就带来一个问题：如果注册时随便分配角色，两个人可能都叫 `gary`，第二个人会直接接管第一个人的房子。
>
> 所以我在注册接口加了唯一性校验：已被占用的角色返回 **409**，让用户换一个。代价是「注册某角色 = 接管该角色的资产」，这在演示环境是刻意接受的取舍；真实产品应该按 `user_id` 建关系，角色只是头像皮肤。

**再追一层**：为什么不在表里同时存 `user_id`？——那要改 6 张表的关联和所有查询，收益只是让 demo 支持两个 `gary` 共存，不划算；我把取舍写进了 README 的已知局限。

**别踩**：别说「没有这个问题」。如果他真的 clone 下来注册两次同角色，一试就知道。

## 三、前端与体验

### Q9. 倒计时用 `setInterval` 减 1 秒，用户改系统时间/切后台怎么办？

**30 秒答**

> 倒计时不对本地减秒，而是每次都用「服务器时间」重新算剩余。接口额外下发 `serverNow`，前端存下 `skew = serverNow - Date.now()`，之后所有时间都按 `Date.now() + skew` 算。这样用户把系统时间拨快两小时也没用。
>
> 另外两个细节：每 30 秒静默对时一次（不打断用户正在输入的价格）；标签页切回前台立即补拉一次，因为后台标签的定时器会被浏览器降频，回来时数字可能是旧的。

**再追一层**

> 校准是**静默**的：只更新数据，不重置输入框，也不弹提示。我还加了个「请求序号」，同一时刻可能有多个请求在飞，只认最后一次返回，避免旧结果覆盖新结果。

**怎么验证的**：打开两个页面，其中一个用 `Date.now` 注入 7 秒偏移，两个页面显示的剩余时间完全一致，且都提示「本机时间偏差 7 秒，已按服务器时间显示」。

**别踩**：别说「用 WebSocket 推时间」，你没做。

### Q11. 站内消息是怎么做到「不用刷新就能看到」的？

**30 秒答**

> 一开始这里是漏的：后端写出了「你的出价被超越了」这条消息，前端也有拉取接口，但只有登录时拉过一次快照，之后再没调用过——用户不刷新页面永远看不到。
>
> 修法是三层：进消息页强制拉一次；全局每 60 秒轮询一次（页面不可见时跳过）；出价成功后立刻拉一次。最后这条最关键，让「被超越」几乎是即时的。

**再追一层**：为什么不用 WebSocket？——单机 demo 为一条通知引入长连接和重连逻辑，复杂度收益不匹配；轮询 60 秒对「拍卖被超越」这种秒级事件确实偏慢，所以补了「出价成功主动拉」这条捷径。

**别踩**：别说「实时推送」。是轮询 + 事件触发，讲清楚更可信。

## 四、工程与交付

### Q12. 为什么做双驱动？生产用哪个？

**30 秒答**

> 业务代码只依赖 `all / get / run / tx` 四个方法，底下可以是 `mysql2` 也可以是 `node:sqlite`，切换只改 `DB_CLIENT`。目的不是炫技，是**降低复现成本**：别人 clone 下来没装 MySQL 也能 `npm run dev:all` 直接跑起来。生产环境走 MySQL，SQLite 主要给测试和快速演示。

**再追一层**：两个驱动的差异靠一层适配吸收——列名 `snake_case ↔ camelCase` 的转换、事务的开启方式、`DATETIME` 在 MySQL 驱动里会还原成 `Date` 而 SQLite 给字符串（这个踩过，`msOf()` 里两种都接住）。

**别踩**：❌「自研 ORM」——只是统一了四个方法的签名，别夸大。

### Q13. 你怎么证明「数据真的落库了」，而不是前端演的？

**30 秒答**

> 端到端测试不只断言 UI 文字，关键断言都回查数据库或直接打接口：比如出价后，除了看页面价格变了，还会 `GET /auctions/:id/bids` 确认 `bids` 多了一条、`bid_count` 加了 1、最终价等于刚才的出价。101 项里有一批是这种「双通道校验」。

**再追一层**：测试最后会调 `/reset` 把演示数据恢复，所以可以反复跑；`/reset` 会让所有会话失效，所以它必须是最后一条断言——这个顺序问题也踩过。

## 五、压力问题（他可能不客气）

### Q15. 这项目才 50 并发，有什么意义？

> 50 并发不是为了证明「能扛 50 并发」，而是为了**在能观察到冲突的规模下验证正确性**。真正重要的是「同价位 50 个请求只有 1 个成交、不同价位混战时计数三者一致」这个结论，而不是吞吐量数字。要谈吞吐我没有任何数据，也不会编。

### Q16. 如果 QPS 上万，你这套还行吗？

> 分两层看。正确性这层不用改：条件 UPDATE 依然是裁决，行锁只锁一行，热点在单个拍卖 id 上，天然不会全表锁。瓶颈会出现在：一是同一场拍卖的所有请求串行在那一行上，需要用队列把出价请求排队削峰（比如 Redis List 或 MQ 做单写者）；二是每次出价都写 `bids` 表，需要分表或先落日志再异步归档。这两条我都没做，因为当前规模不需要——但我知道瓶颈在哪。

**别踩**：不要顺着他说「加个 Redis 集群、上微服务就好」。说清瓶颈位置比背方案强。

### Q17. 为什么没有单元测试？

> 有取舍：这个项目的风险主要在「并发正确性」和「跨层的数据一致性」，单测覆盖不到，价值密度低。所以我把投入放在端到端（101 项，含回查数据库）和并发压测（17 项）。纯函数的单测确实缺，比如时间格式化、金额取整这些，补起来成本不高但我没补。

### Q18. 这个项目最大的问题是什么？

> 三件事，按严重程度：
> 1. **单租户假设没彻底解决**：角色 id 当身份，注册某角色等于接管该角色的房子和租约。演示没问题，产品化必须改成按 `user_id` 建关系。
> 2. **没有真正的多实例验证**：懒结算和多实例幂等是靠代码推理 + 幂等 SQL 保证的，没有起两个实例实测。
> 3. **前端没有测试**：组件级行为（比如出价按钮的禁用态）全靠端到端覆盖，漏测时会以「页面能开但交互错」的形式暴露。

*（主动说出缺点比被问出来强得多，而且第 2、3 条都是可验证的真话。）*
