## 二、标准版（项目经历，推荐直接用这份）

**小蜗 · 比奇堡租房平台** ｜ 全栈独立开发 ｜ Vue 3 · Vite 6 · Express 4 · MySQL 8 · Redis 7 · Docker

- 独立完成租房 / 二手房 / 法拍房 / 社区四条业务线，26 个路由、16 张表、约 1.3 万行代码；后端抽了一层双驱动数据访问（MySQL ↔ SQLite 切换只改一个环境变量，本地无依赖即可跑）。
- **拍卖出价：把正确性交给数据库。** 不用「先查当前价 → 判断 → 再写回」的读改写（并发下会双写），而是把「最低加价、非本人连续出价、未结束」三个条件全部编进一条 `UPDATE ... WHERE`，以 `affectedRows === 1` 判定胜负。压测：50 并发同价位仅 1 单成功；50 个不同价位混战 38 单成功，出价次数、落库条数、成功次数三者严格一致。
- **Redis 是可选增强，不是依赖。** 分布式锁封装成三态（拿到 token / 被他人占用 / Redis 不可用则直接放行），另用 ZSET 做出价排行榜、固定窗口做限流。实测把 Redis 停掉后出价功能完全不受影响，只是失败重试变多——锁只削峰，正确性由数据库兜底。
- **结算不用定时器。** 在读取路径上做 `settleDue()` 懒结算：到点自动成交、改房源状态、给买卖双方写站内消息。多实例部署也不会重复结算，省掉一套定时任务与分布式调度。
- **倒计时防漂移。** 接口额外下发 `serverNow`，前端算出本机时钟偏差后倒计时统一按服务器时间走；每 30 秒静默校准（不打断用户输入）、切回前台补拉一次。把系统时间拨快 7 秒，页面剩余时间与正常机器完全一致。
- **质量保障。** Puppeteer 端到端 101 项断言（不只看 UI，还回查数据库确认真的落库）+ 独立并发压测脚本 15 项断言；`npm test` 跑完自动重置演示数据。Docker 多阶段构建 + Compose 三容器（应用 / MySQL / Redis）部署，镜像 333MB、非 root 运行、带健康检查。

## 三、精简版（简历空间紧张时，保留 3 条）

- 独立开发全栈租房平台（Vue 3 + Express + MySQL + Redis，26 路由 / 16 表 / 约 1.3 万行），含法拍房竞价、二手房意向、社区互动等模块。

## 四、技术深度版（项目详情页 / 答辩 PPT 一页）

问题 → 方案 → 验证，每行都能展开讲：

1. **超卖**：读改写有竞态 → 条件 UPDATE + affectedRows → 50 并发压测证明只 1 单成功。
2. **锁的定位**：一开始用 Redis 锁做互斥，但锁挂了就出不了价 → 改成三态封装，锁失败即放行，数据库兜底 → 拔掉 Redis 全流程验证。
3. **结算时机**：定时任务在多实例下会重复执行 → 读时懒结算 → 同一场次反复读取只结算一次。
4. **时间不可信**：浏览器本地时间可改、后台标签页定时器会被降频 → `serverNow` 对时 + 静默校准 → 拨快本机时间验证无偏差。
5. **数据归属**：账单 / 预约 / 消息原本全表共享 → 补 `user_id` + 迁移回填 + 越权校验（403/404）→ 新账号看不到他人数据、拿到 id 也改不了。
6. **地图**：官方 `MarkerCluster` 在 JS API 2.0 下渲染为空 → 放弃插件，改用「分区槽位 + 紧凑价格标签」自解重叠 → 13 个点位零遮挡、430px 无横向溢出。

## 五、面试高频追问 & 一句话答法

| 追问 | 怎么答 |
| --- | --- |
| 「条件 UPDATE 具体怎么写的？」 | 把 `status='live' AND end_at > now AND price >= 当前价+步长 AND (领先者为空 OR 领先者<>我)` 全放进 WHERE，`changes===1` 才算赢，事务里再插一条出价记录。 |
| 「那 Redis 锁还有必要吗？」 | 有必要但不是正确性来源：它让同一场次的并发排队几毫秒，减少无谓的失败重试；锁封装成三态，Redis 不可用时返回 undefined 直接放行。 |
| 「50 并发只成功 1 个，是不是锁挡住了？」 | 特意做了对照组：第一轮绕过锁直接打库，结果一样是 1 个成功，证明是数据库的条件更新在裁决。 |
| 「为什么不用消息队列 / 定时任务结算？」 | 规模不需要，且定时任务多实例要加分布式调度；懒结算把「何时结算」变成读路径的幂等操作，更简单也更好验证。 |
| 「多用户数据怎么隔离的？」 | 租约用角色 id（tenant/owner 双视角），账单/预约/消息用 user_id；写接口全部带归属校验，越权返回 403/404。 |
| 「为什么角色要唯一？」 | 房源 owner_id、拍卖 seller_id 都存角色 id，同一角色两个账号会互相接管资产，所以注册时校验唯一。 |

## 六、不要写（会被问穿）

- ❌ 「高并发」「海量数据」「百万级 PV」——项目是 50 并发的验证规模，写大词一问就露。
- ❌ 「用分布式锁解决了超卖」——恰好相反，锁不是正确性来源，说错方向比不说更糟。
- ❌ 「多租户 SaaS」——实际是单实例 + 按账号隔离，角色扮演型 demo。写「多用户数据隔离」是准确的。
- ❌ 「微服务架构」——它是单体 Express + 三个容器，别硬套。
- ❌ 「自研 ORM / 自研缓存」——数据访问层只是统一了双驱动的 all/get/run/tx，别夸大。
- ❌ 只写技术栈清单（Vue3 + Express + MySQL…）——那是课程作业的写法，要写「为了解决什么，选了什么，怎么验证的」。
