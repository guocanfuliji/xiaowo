### B. 一段话版（288 字，适合网申填写框）

> 独立开发全栈租房平台「小蜗」：Vue 3 + Express + MySQL + Redis，26 个路由、16 张表、约 1.3 万行代码，覆盖租房、二手房、法拍房与社区四条业务线。最核心的难点是法拍房出价的并发正确性——没有用「查当前价、判断门槛、再写回」的读改写，而是把加价门槛、出价人校验、结束时间编进一条条件 UPDATE，以 affectedRows 判定胜负；50 并发同价位压测只有 1 单成交，50 个不同价位混战无超卖、无重复计数。Redis 只承担削峰、排行榜与限流，三态锁在不可用或已被占用时直接放行，拔掉 Redis 出价照常可用。边界情况也做了处理：结算用读路径懒结算替代定时任务，多实例不重复；倒计时按服务端时间校准，篡改本机时间不产生偏差；账单、预约、消息按账号隔离，越权写操作返回 403。质量方面有端到端 101 项断言与 17 项并发断言，Docker Compose 一键部署（镜像 333MB、非 root 运行）。

### C. 技术特点 / 难点 / 解决 版（约 400 字，推荐）

> **小蜗 · 比奇堡租房平台**｜全栈独立开发｜Vue 3 · Vite 6 · Express 4 · MySQL 8 · Redis 7 · Docker
> 代码：github.com/guocanfuliji/xiaowo｜26 页面 · 16 表 · 约 1.35 万行 · 端到端 101 项 / 并发 17 项断言
>
> **技术特点**
> - 拍卖把校验下沉成一条条件 `UPDATE`：加价门槛、出价人、截止时间全部写进 `WHERE`，`affectedRows` 判胜负，不存在读改写窗口。
> - Redis 只做「可整体缺席」的增强：三态锁只削峰，ZSET 排行可回源重建，限流用固定窗口；Redis 停了业务照常。
> - 结算不用定时器：读路径懒结算 + `status='live'` 幂等更新；数据层双驱动，MySQL 与 SQLite 改一个环境变量即可切换。
>
> **难点与解决**
> - 同价位并发会超卖 → 条件 `UPDATE` 裁决 → 50 并发仅 1 单成交，价格只被写一次。
> - 锁让出价变成单点（Redis 一停全部 409）→ 锁降级为三态、拿不到即放行 → 停掉 Redis 后出价 / 成交 / 结算全通。
> - 倒计时可被本机时间篡改 → 接口下发 `serverNow`，前端存偏差并每 30 秒静默对时 → 拨快 7 秒与正常机器显示一致。
> - 账单 / 预约 / 消息全表共享，拿到 id 就能操作他人数据 → 补 `user_id` + 迁移回填 + 归属校验 → 越权付款 403、删他人消息 404。
>
> **结果**：端到端 101 项 + 并发 17 项断言全通过；Docker Compose 三容器一键复现，镜像 333MB、非 root。

### D. 口述故事卡（面试用，挑一个讲 1~2 分钟）

**① 出价并发：为什么最后不靠锁**

- S：最初的做法是「Redis 分布式锁 + 读当前价、判断、再写回」，逻辑上很顺。
- T：但有一次我把 Redis 停掉复测，发现所有出价都返回 409——因为锁拿不到就直接抛错了。
- A：把锁改成三态（拿到返回对象 / 被占返回 `false` / Redis 不可用返回 `undefined` 直接放行），同时把胜负判定下沉成一条条件 `UPDATE`，用 `affectedRows` 裁决。
- R：Redis 全停也能正常出价；50 并发同价位时，开锁与不开锁结果都是 1 单成交——证明正确性来自数据库，不是锁。

**② 站内通知不刷新：接口写了但没人调用**

- S：出价被超越时后端会写一条站内消息，消息页也能正常显示列表。
- T：但实测发现：不手动刷新页面，用户永远看不到新消息。
- A：排查发现消息只在登录时的快照里拉过一次，`Api.messages.list()` 定义了却没有任何调用点。补了三层：进消息页强制拉取、全局 60 秒轮询（页面不可见跳过）、出价成功后立刻拉一次。
- R：两个账号互相出价验证，被超越的一方无需刷新即可看到提醒。

**③ 数据隔离：从「全表共享」到按账号过滤**

- S：账单、预约、消息原本没有归属字段，任何人拿到 id 就能操作别人的数据。
- T：先补隔离，且不能破坏已有演示数据。
- A：三张表加 `user_id` 并写迁移回填到演示账号；写接口全部加归属校验（越权付款 403、删他人消息 404，避免暴露存在性）；租约按 `tenant_id OR owner_id` 双视角过滤。另外发现角色 id 被当身份用，注册时补了唯一性校验（409）。
- R：新账号登录后消息 / 账单 / 预约均为 0；跨账号付款 403、删消息 404；`read-all` 不影响他人未读数。

## 二、标准版（项目经历，推荐直接用这份）

**小蜗 · 比奇堡租房平台** ｜ 全栈独立开发 ｜ Vue 3 · Vite 6 · Express 4 · MySQL 8 · Redis 7 · Docker

- 独立完成租房 / 二手房 / 法拍房 / 社区四条业务线，26 个路由、16 张表、约 1.3 万行代码；后端抽了一层双驱动数据访问（MySQL ↔ SQLite 切换只改一个环境变量，本地无依赖即可跑）。
- **拍卖出价：把正确性交给数据库。** 不用「先查当前价 → 判断 → 再写回」的读改写（并发下会双写），而是把「最低加价、非本人连续出价、未结束」三个条件全部编进一条 `UPDATE ... WHERE`，以 `affectedRows === 1` 判定胜负。压测：50 并发同价位仅 1 单成功；50 个不同价位混战 38 单成功，出价次数、落库条数、成功次数三者严格一致。
- **Redis 是可选增强，不是依赖。** 分布式锁封装成三态（拿到 token / 被他人占用 / Redis 不可用则直接放行），另用 ZSET 做出价排行榜、固定窗口做限流。实测把 Redis 停掉后出价功能完全不受影响，只是失败重试变多——锁只削峰，正确性由数据库兜底。
- **结算不用定时器。** 在读取路径上做 `settleDue()` 懒结算：到点自动成交、改房源状态、给买卖双方写站内消息。多实例部署也不会重复结算，省掉一套定时任务与分布式调度。
- **倒计时防漂移。** 接口额外下发 `serverNow`，前端算出本机时钟偏差后倒计时统一按服务器时间走；每 30 秒静默校准（不打断用户输入）、切回前台补拉一次。把系统时间拨快 7 秒，页面剩余时间与正常机器完全一致。
- **质量保障。** Puppeteer 端到端 101 项断言（不只看 UI，还回查数据库确认真的落库）+ 独立并发压测脚本 17 项断言；`npm test` 跑完自动重置演示数据。Docker 多阶段构建 + Compose 三容器（应用 / MySQL / Redis）部署，镜像 333MB、非 root 运行、带健康检查。

## 四、技术深度版（项目详情页 / 答辩 PPT 一页）

问题 → 方案 → 验证，每行都能展开讲：

1. **超卖**：读改写有竞态 → 条件 UPDATE + affectedRows → 50 并发压测证明只 1 单成功。
2. **锁的定位**：一开始用 Redis 锁做互斥，但锁挂了就出不了价 → 改成三态封装，锁失败即放行，数据库兜底 → 拔掉 Redis 全流程验证。
3. **结算时机**：定时任务在多实例下会重复执行 → 读时懒结算 → 同一场次反复读取只结算一次。
4. **时间不可信**：浏览器本地时间可改、后台标签页定时器会被降频 → `serverNow` 对时 + 静默校准 → 拨快本机时间验证无偏差。
5. **数据归属**：账单 / 预约 / 消息原本全表共享 → 补 `user_id` + 迁移回填 + 越权校验（403/404）→ 新账号看不到他人数据、拿到 id 也改不了。
6. **地图**：官方 `MarkerCluster` 在 JS API 2.0 下渲染为空 → 放弃插件，改用「分区槽位 + 紧凑价格标签」自解重叠 → 13 个点位零遮挡、430px 无横向溢出。

## 五、面试高频追问 & 一句话答法

> 完整版见 **[面试追问准备.md](./面试追问准备.md)**：18 个问题，每题含「他为什么问 / 30 秒答法 / 再追一层 / 别踩」，
> 另附四轮压测对照表、数字速查卡与「讲不清就别写」红线清单。下表只是速览。

| 追问 | 怎么答 |
| --- | --- |
| 「条件 UPDATE 具体怎么写的？」 | 把 `status='live' AND end_at > now AND price >= 当前价+步长 AND (领先者为空 OR 领先者<>我)` 全放进 WHERE，`changes===1` 才算赢，事务里再插一条出价记录。 |
| 「那 Redis 锁还有必要吗？」 | 有必要但不是正确性来源：它让同一场次的并发排队几毫秒，减少无谓的失败重试；锁封装成三态，Redis 不可用时返回 undefined 直接放行。 |
| 「50 并发只成功 1 个，是不是锁挡住了？」 | 特意做了对照组：第一轮绕过锁直接打库，结果一样是 1 个成功，证明是数据库的条件更新在裁决。 |
| 「为什么不用消息队列 / 定时任务结算？」 | 规模不需要，且定时任务多实例要加分布式调度；懒结算把「何时结算」变成读路径的幂等操作，更简单也更好验证。 |
| 「多用户数据怎么隔离的？」 | 租约用角色 id（tenant/owner 双视角），账单/预约/消息用 user_id；写接口全部带归属校验，越权返回 403/404。 |
| 「为什么角色要唯一？」 | 房源 owner_id、拍卖 seller_id 都存角色 id，同一角色两个账号会互相接管资产，所以注册时校验唯一。 |

## 六、不要写（会被问穿）

- ❌ 「高并发」「海量数据」「百万级 PV」——项目是 50 并发的验证规模，写大词一问就露。
- ❌ 「用分布式锁解决了超卖」——恰好相反，锁不是正确性来源，说错方向比不说更糟。
- ❌ 「多租户 SaaS」——实际是单实例 + 按账号隔离，角色扮演型 demo。写「多用户数据隔离」是准确的。
- ❌ 「微服务架构」——它是单体 Express + 三个容器，别硬套。
- ❌ 「自研 ORM / 自研缓存」——数据访问层只是统一了双驱动的 all/get/run/tx，别夸大。
- ❌ 只写技术栈清单（Vue3 + Express + MySQL…）——那是课程作业的写法，要写「为了解决什么，选了什么，怎么验证的」。
